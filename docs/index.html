What does plan approval guarantee?

Approving a plan feels like approving an outcome. This lab follows one ConfigMap field through four boundary tests in which a second writer reaches the same object, and records what the approval was actually bound to. In this pinned setup exactly one of the four was stopped, by the saved plan's stale-plan check, not by the state lock. A pre-apply check you can take to your own pipeline, which compares the live values with the approved plan only at the paths the plan changes, blocked conflicting edits and let everything else through.

The setup

One object, one field: ConfigMap t27/t27, data.value. OpenTofu keeps its state in the Kubernetes backend with a lease-based lock. A person triggers the OpenTofu CLI; no OpenTofu controller is involved. The second writer is a separate service account with its own token in TC-01 and TC-02 (so the API server's audit log records it as a different user), a competing OpenTofu apply on the shared state in TC-03, and Flux in TC-04.

Every scenario runs on a fresh k3d cluster. Recorded for each: what the approval was bound to, the planned actions, state serial and lineage, the writes the audit log captured, field managers, final values, and the exit code and rejection reason of every command.

The lock did not stop TC-03. A lock only arbitrates operations that run at the same time. The competing apply finished before the earlier plan was applied. What refused the plan is the state serial it carries: the state had moved on. In TC-02 the edit went straight to the API and did not touch the state, so neither mechanism had anything to detect.

The lock itself works: in a separate step of TC-03, before the plan is saved, a second runner is refused with Error acquiring the state lock while another apply holds it.

The pre-apply check

One question, right before tofu apply <plan>: at every path the approved plan changes, is the live value still the value recorded in the plan? gate/plan-drift-gate.sh uses only OpenTofu and jq; the comparison does not depend on the provider.

tofu plan -out reviewed.tfplan -var-file=prod.tfvars     # reviewed and approved
gate/plan-drift-gate.sh reviewed.tfplan -var-file=prod.tfvars && tofu apply reviewed.tfplan
# exit 0 apply, 1 block (re-plan and re-approve), 2 could not decide (treat as block)

It makes a refresh-only saved plan, which reads the live infrastructure without changing it or the state, and compares its values with the reviewed plan's recorded values, only at the paths the plan changes (leaf paths for an update; the whole resource for a create, delete or replace). An empty map or list counts as null. It fails closed on unreadable or errored plans, a refresh with different variables, options that narrow the refresh, imports, moves and deposed objects. 71 unit tests on synthetic plans run without tofu or a cluster.

The exit code of tofu plan -refresh-only -detailed-exitcode was 2 on all six paths, and the JSON drift report counted one change on all six: the provider stores empty maps as null (binary_data, metadata.annotations, metadata.labels) and reads them back as {}. A gate on either would block every plan.

Not checked: a write between the check and the apply; the inputs the plan was computed from; values the provider does not read back; objects outside the state; writes after the apply (TC-04). Measured on one provider and one resource type.

The stale-plan check compares the lineage and serial of the state a saved plan was made from with the current state (OpenTofu v1.12.6, internal/backend/local/backend_local.go, lines 347–375); it does not read the live object. That is why TC-03 was refused and TC-02 was not.

Three checks this implies for a pipeline:

  1. Does the approval bind a configuration revision or the exact saved plan that will be applied?
  2. Does anything compare the live object with the reviewed plan before applying?
  3. Which other writers can change the same fields during or after the apply?

Counting writes, not calls

In TC-04 Flux's kustomize-controller made 5 successful API calls on the object in the 120-second window: 4 dry runs (its drift detection; nothing is written) and 1 persisted server-side apply, the only field change it made, B → C. That write happened right after the Kustomization was resumed, before the three requested reconciliations, which found nothing to change. A request body cannot tell a write from a no-op here, because a server-side apply sends the desired value; the checks therefore order the persisted writes by resourceVersion and compare each with the one before it.

What this does not say

  • Not a vulnerability report: no mechanism was bypassed; each did what it is for.
  • Not a general rule: one pinned setup (OpenTofu 1.12.6, hashicorp/kubernetes 2.38.0, Flux 2.9.5, k3s v1.37.0-k3s1).
  • Not shown to be independent of k3s: a repeat on a second distribution has not been run.
  • Nothing about OpenTofu controllers: none was run.
  • Not a comparison of server-side apply options: TC-02 saw no conflict, which depends on how the provider writes.
  • Not a complete fix: the check covers the paths the plan changes, not the plan's inputs, and nothing between the check and the apply.

Run it

Ubuntu 24.04 or 26.04 with network access for the first install.

git clone https://github.com/graphsentinel/tofu-plan-approval.git
cd tofu-plan-approval
scripts/platform.sh install      # missing Ubuntu packages; pinned tofu, flux, k3d, kubectl into bin/
scripts/platform.sh cluster-up   # the lab's k3d cluster and registry
RUNS=2 scripts/lab.sh all        # build, install, the full experiment twice, checks, summary

On a 4-CPU, 8 GB VM one full run (six scenarios, each on a fresh cluster) took about 6 minutes. Without a cluster, scripts/verify.sh --reference re-runs every check that reads a recorded run against the published reference runs. Details are in the README.

  • Clean-VM runs (2026-10-15): Ubuntu 26.04 (5 runs, then 1 after a reinstall) and 24.04 (1 + 1), from zero; all 8 matched the expected 19 check results and 57 measurement rows, TC-01 to TC-06. One of them is published in full.
